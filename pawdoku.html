PawDoku

A mobile logic puzzle that forced me to stop thinking only about mechanics and start thinking about the whole product.

01 / Context

What the project became

PawDoku is a pet-themed logic puzzle game where each row, column and region follows placement rules. The first version was about getting the puzzle to work. The finished project had to handle much more: mistakes, lives, coins, progression, boosters, daily content, persistence, player feedback, monetization, store services and release behavior.

That shift is the main reason I use PawDoku as my primary portfolio project. It shows the difference between building a mechanic and owning a game long enough to ship it.

02 / Core systems

The gameplay layer

01

Puzzle validation

Placement rules, invalid-move detection and clear player feedback for mistakes.

02

Lives & economy

Wrong moves affect lives and coins, tying moment-to-moment decisions to the wider game loop.

03

Boosters

Hint, undo, retry and streak-related tools integrated into gameplay instead of bolted on afterward.

04

Daily challenge

A separate repeatable challenge flow with lives, streak behavior and reward logic.

03 / Product systems

The parts players only notice when they break

save

Persistence & cloud flow

Player progress had to survive sessions and integrate with Google Play sign-in. I also built a conflict prompt so a returning player can decide whether to use cloud data instead of silently overwriting local progress.

mobile

Ads without wrecking the first session

Banner, interstitial and rewarded formats are handled separately, with onboarding-aware gating and purchase logic so remove-ads does not accidentally remove rewarded choices the player still wants.

store

IAP & consent

Coin packs, booster packs, purchase handling, first-purchase feedback and consent flow were treated as product systems with failure states, not just button callbacks.

ops

Analytics & notifications

Important actions such as level starts, completions, failures, claims, purchases and ad outcomes are instrumented so behavior can be understood after release. Notifications support daily and inactivity return loops.

04 / Production

Getting it out of the editor

Shipping exposed a different category of problems: safe areas, device layouts, SDK behavior, mobile lifecycle cases, store requirements, consent, build configuration, debugging release-only issues and making sure the tutorial cannot leave the player in an impossible state.

I handled the Android release process and the Google Play integrations myself. That work is less visible in a trailer, but it is the part of PawDoku that most changed how I approach later projects.

05 / What I learned

A prototype proves an idea. A release proves everything around it.

PawDoku made me much less impressed by a mechanic that works once. I now look for restart behavior, persistence, failure recovery, onboarding, device constraints and what happens after the hundredth play session — because those are the things that decide whether a system is actually finished.
